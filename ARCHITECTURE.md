## 1. Принятые решения

**Язык — C++20**, сборка CMake, GCC или Clang.

| Критерий | C++20 | Rust |
|---|---|---|
| Скорость, SIMD, работа с битами | равны | равны |
| Библиотеки (libsais, zstd — на C) | подключаются напрямую | через обёртки |
| Безопасность памяти декодера | дисциплина + санитайзеры + фаззинг | гарантируется языком |
| Автор читает код | легче | труднее |
| v1 была на | C++ | — |

Rust лучше только по безопасности памяти. Этот недостаток C++ закрывается правилами из раздела 8.
Второй язык не вводится.

**Зависимости**: только libsais 2.12.1 (Apache-2.0), лежит в `third_party/`. XXH64 и range coder написаны свои.

## 2. Формализация идеи автора

| Термин автора | Строгий аналог |
|---|---|
| «пиксель» | символ алфавита (байт, позже — поле или бит) |
| ссылка-координата | фраза LZ77 `(смещение, длина)` или директива макросхемы |
| «специальный пиксель» для частой строки | нетерминал грамматики (SLP, Re-Pair) |
| «координаты координат» | сжатие потока ссылок вторым уровнем: коллажная система (грамматика + усечение `X → K[l..r]`), Re²Pair, в пределе GSLP |

Точнее всего идею описывает **коллажная система**: правила конкатенации, повторения и вырезания подстроки
из уже построенного правила. Это «LZ77 поверх правил», то есть ссылка на ссылку.

Что говорит приложенное теоретическое исследование (приоритетный источник для этого раздела):

1. **На обычных стационарных данных глубина больше 2 не даёт ничего.** После первого уровня вся энтропия
   уходит в смещения, которые почти равномерны. Второй уровень выигрывает только на длинах фраз,
   порядка `n·log log n / log n` бит. Уровни 3 и выше асимптотически бесполезны.
2. **Многоуровневость строго выигрывает в трёх случаях**: дальние повторы при малом окне (радиус видимости
   растёт как произведение средних длин фраз по уровням), коллекции версий одного и того же, самоподобные данные.
3. **Правило остановки**: уровень `k` оставляем, только если экономия в теле больше стоимости его заголовка
   и словаря. Это тот же принцип MDL, что и «фильтр включается только при доказанном выигрыше».

Вывод: идея автора не годится как единственное ядро универсального архиватора, но имеет три законных места:

- **L1. Дальний слой перед блоками** [план]: поиск повторов по всему файлу (rolling hash, Prefix-Free Parsing),
  применённый рекурсивно к собственному потоку ссылок. Заодно лечит главный недостаток независимых блоков
  BWT — потерю повторов между блоками.
- **L2. Второй уровень над потоком ссылок в LZ-режиме** [гипотеза]: макро-ссылки на повторяющиеся цепочки
  `(lit_len, match_len, offset)` и марковский кэш переходов между смещениями вместо плоского `rep0..rep3`.
- **L3. Грамматическое ядро для сильно повторяющихся данных** [гипотеза]: включается анализатором, когда
  оценка повторяемости высока (логи, версии, геномы).

Эксперимент E3 измеряет вклад каждого уровня отдельно. Критерии отказа взяты из исследования:
L2 отбрасывается, если чистый выигрыш меньше 0,4 % на структурированных данных или распаковка замедляется
больше чем на 12 %.

Оговорки к исследованию: при копировании пропали все формулы (на их месте пустые символы); ссылки на работы
2026 года я пока не сверял с первоисточниками; скорости «сотни МБ/с» в нём — оценки, а не замеры.

## 3. Кандидаты ядра

| Ядро | Оценка | Решение |
|---|---|---|
| A: LZ77 + оптимальный парсинг + ANS | лучшая скорость распаковки, сжатие хуже BWT | [план] режим `fast`; место для L2 |
| B: BWT + адаптивный кодер | лучший баланс размер/скорость на CPU; вероятный родственник v1 | **[сделано] первым** |
| C: грамматика | сильна только на повторяющихся данных | [гипотеза] слой L1/L3, не ядро |
| D: побитовый context mixing | максимум сжатия, на порядок медленнее | [план] режим `max` |

Выбор B первым обоснован целью «не хуже v1»: по обзорным данным класс BWT сжимает сильнее LZMA и быстрее его.
Окончательный выбор — по эксперименту E2, а не по этой таблице.

## 4. Конвейер

Блок кодируется цепочкой стадий, каждая отображает байты в байты:

```
raw --stage[0]--> ... --stage[k-1]--> payload
```

Цепочка (идентификатор стадии + её параметры) записана в заголовке блока, поэтому архив сам описывает,
как его распаковать. Декодер применяет обратные стадии с конца. Пустая цепочка = блок сохранён как есть.

Сейчас цепочек две: `bwt > cm1` и `x86 > bwt > cm1`. Интерфейс стадии (`src/stages.hpp`):

```
encode(in, params_out) -> out          // вход доверенный
decode(params, in, max_out) -> out     // вход недоверенный, обязана всё проверять
```

Диапазоны идентификаторов (часть формата, значения не переиспользуются):

| Диапазон | Назначение | Занято |
|---|---|---|
| 0x10–0x1F | структурные преобразования | 0x10 `bwt`; план: LZP, дальний слой L1 |
| 0x20–0x2F | модели и энтропийные кодеры | 0x22 `cm1`; 0x20 и 0x21 — версии разработки, выведены |
| 0x30–0x3F | фильтры (BCJ, delta, shuffle) | 0x30 `x86`; 0x32 `arm64` (BL, плотность ≥ 1 на 80 Б) |
| 0x40–0x4F | пересжатие (Deflate, JPEG) | — |
| 0x50–0x5F | LZ-ядра | — |
| 0x60–0x6F | грамматики и «ссылки на ссылки» | — |
| 0xF0–0xFF | эксперименты, в выпущенных архивах запрещены | — |

Изменился алгоритм стадии — она получает новый идентификатор. Старые архивы читаются всегда.

Место для анализа и выбора цепочки — функция `encode_block` в `src/stages.cpp`. Правило для будущих
вариантов: кандидат пробуется на образце, включается при доказанном выигрыше, иначе откат.

## 5. Формат контейнера `.apx`, версия 0.1

Все числа little-endian. `varint` — LEB128, не длиннее 10 байт. `check` — младшие 32 бита XXH64 от всех
предыдущих байт того же заголовка.

**Заголовок файла, 12 байт**

| Поле | Размер | Значение |
|---|---|---|
| magic | 4 | `APXL` |
| major | 1 | 0. Другое значение — читатель отказывается |
| minor | 1 | 1. Информационное |
| block_log2 | 1 | 10..30. Ни один блок не больше `2^block_log2` байт |
| flags | 1 | 0. Ненулевое — читатель отказывается |
| check | 4 | |

**Кадр блока, тип 0x01**

| Поле | Размер | Значение |
|---|---|---|
| type | 1 | 0x01 |
| raw_size | varint | 1..`2^block_log2` |
| comp_size | varint | 0..raw_size |
| nstages | 1 | 0..8. При 0 блок сохранён, `comp_size == raw_size` |
| стадии | nstages × (id:1, plen:1, params:plen) | в порядке кодирования |
| hash | 8 | XXH64 исходных байт блока |
| check | 4 | |
| payload | comp_size | |

**Конечный кадр, тип 0x02** — обязателен, после него должен быть конец файла.

| Поле | Размер | Значение |
|---|---|---|
| type | 1 | 0x02 |
| total_raw | varint | сумма raw_size всех блоков |
| nblocks | varint | число блоков |
| stream_hash | 8 | XXH64 от склеенных hash всех блоков; ловит потерю и перестановку блоков |
| check | 4 | |

**Кадры расширения, типы 0x80–0xFF**: `type, varint len, check, len байт`. Читатель, не знающий тип,
пропускает кадр. Сюда лягут метаданные файлов, обученные словари, описания моделей и «язык битов».

Параметры стадий: `bwt` — varint первичного индекса (1..n); `cm1` — varint размера результата; `x86` — без параметров.
Поток range coder'а: ведущий нулевой байт не пишется, хвостовые нули обрезаются, декодер дополняет поток нулями
(поэтому `comp_size` может быть 0: 300 КБ нулей занимают в payload 0 байт).

Накладные расходы на несжимаемых данных: 12 + 17 байт на файл и около 20 байт на блок. На 1 МиБ случайных
данных — 49 байт.

## 6. Ядро B: BWT + CM1 [сделано]

BWT собирает символы с похожим контекстом вместе, после него идут длинные участки из одного-двух символов.
CM1 (`src/stage_cm1.cpp`) кодирует каждый символ короткой цепочкой двоичных решений:

- **A**: символ равен предыдущему `c1`? Попадание стоит одного решения.
- **B**: иначе, равен ли он `c2` — символу, который был перед `c1`?
- **L**: иначе сам байт, 8 решений от старшего бита («литерал»).

Каждое решение предсказывают несколько адаптивных таблиц вероятностей под разными контекстами:
длина текущей серии, пара `c1,c2`, третий недавний символ `c3`, а для A и B — локальная частота:
сколько раз `c1` и `c2` встретились среди последних 32 символов. Всего 12 таблиц: 4 для A, 3 для B,
5 для литералов; ещё 6 таблиц первой версии убраны по результатам абляции (вместе давали 0,025–0,04 %).
Предсказания складывает логистический миксер с онлайн-обучением весов, уточняет ступень APM,
итоговая вероятность идёт в двоичный range coder с 16-битной точностью.

Измерено на 8 файлах Silesia: в среднем 4,2 решения на символ вместо 8; литералы — 35 % символов,
но 80 % выходных байт. Улучшать нужно в первую очередь их.

Разложение A/B/L — собственное решение. Прямое побитовое кодирование на тех же таблицах сжимает
на 0,26 % лучше, но в 1,7 раза медленнее, поэтому для режима balanced оставлено A/B/L.
Все проверенные варианты модели с цифрами — в BENCHMARKS.md.

**Фильтр x86** (`src/stage_x86.cpp`): в командах CALL/JMP относительный адрес заменяется абсолютным,
одинаковые вызовы становятся одинаковыми байтами. Меняются только младшие 3 байта операнда и только
когда старший равен 0x00 или 0xFF, поэтому обратное преобразование точное. Включается, когда в блоке
не меньше одного кандидата на 200 байт [порог — гипотеза, проверить на большем наборе].

Память: около 8 байт на байт блока на поток при сжатии с проверкой, плюс около 3 МБ на модель.

## 7. Параллелизм

[сделано] Блоки независимы. Читается пачка блоков, они обрабатываются параллельно, результаты пишутся
по порядку. Байты архива зависят только от входа и размера блока — не от числа потоков и не от лимита памяти.
Лимит памяти `-M` уменьшает размер пачки.

Цена независимых блоков: повторы между блоками теряются. [план] лечится слоем L1 (раздел 2) и большим
блоком; [план] потоковый пул вместо пачек; [гипотеза] многопоточный libsais для одного огромного блока.

## 8. Безопасность и надёжность

- **Проверка на лету** [сделано]: каждый закодированный блок распаковывается и сравнивается с оригиналом
  до записи. Включена по умолчанию, отключается `--no-verify`. Цена — время распаковки блока.
- **Хранить** [сделано]: если кодированный блок не меньше исходного строго, пишется исходный.
- **Детерминизм** [сделано]: в кодеке нет чисел с плавающей точкой. Логистическая функция берётся из
  таблицы, вшитой в код. Кодер и декодер исполняют одну и ту же шаблонную функцию модели.
- **Недоверенный вход** [сделано]: все чтения через проверяющие границы классы; размеры проверяются до
  выделения памяти; заголовок кадра проверяется контрольной суммой до чтения payload; промежуточные буферы
  не больше `raw_size·1,125 + 1024`; блок, требующий памяти сверх лимита, отвергается.
- **Вывод** [сделано]: пишется во временный файл и переименовывается при успехе. Существующий файл без `-f`
  не перезаписывается.
- **Тест порчи** [сделано]: 850 испорченных архивов (включая блоки с фильтром x86) (биты, байты, обрезание, мусор) — все либо отвергнуты,
  либо распакованы верно, под ASan и UBSan без единого срабатывания.
- [план] Настоящий фаззинг (libFuzzer) декодера и отдельно обратного BWT из libsais на произвольных данных.

| Режим | Состав | Цель, равное число потоков | Состояние |

## 10. Обучение и расширение [план]

- Обученные словари и модели хранятся в кадрах расширения и адресуются по хешу содержимого;
  блок ссылается на них параметром стадии. Архив без нужного словаря не распаковывается молча — ошибка.
- «Язык битов»: описание разбора формата становится стадией-фильтром (разделение полей), а выученные
  «планы» — выбором цепочки стадий в `encode_block`.
- Цикл ИИ-улучшения: оценщик = суммарный размер на корпусе при ограничениях на скорость и память +
  обязательный бит-в-бит; итог считается на отложенном наборе. Первая цель — константы и контексты CM1.

| H2: скорость от многопоточности | не проверена: v1 шла на сервере с неизвестным числом ядер. В один поток ядро B быстрее 7-Zip в 3,7 раза и без этого |

Восстановить v1 точно нельзя: таблицы тестов утеряны. Проверяется только совместимость профиля.

## 12. Риски и открытые вопросы

1. Распаковка медленная (7 МиБ/с на ядро). Для сценария «один раз сжать, много раз читать» нужен режим fast.
2. Бинарные данные без x86-кода (mozilla, sao, samba): BWT проигрывает LZMA 4–19 %. Сегментация и
   перестановка полей в bsc дают на них не больше 2–3 %, то есть нужен другой движок (LZ) с выбором по блоку.
3. На английском тексте простая модель BCM/bzip3 лучше CM1 на 1 % (dickens, enwik8). Причина не выяснена:
   дело не в источниках информации, а в способе смешивания (линейное + SSE против логистического).
4. Блоки по 32 МиБ теряют дальние повторы. Лекарство — слой L1.
5. Безопасность обратного BWT в libsais на произвольном входе подтверждена только тестом порчи, не фаззингом.
6. Все замеры сделаны на одном ядре в песочнице; на Ryzen 5 8600G и в 12 потоков нужно повторить.

   ядре проверено и не ускоряет (даже замедляет на 10–25 %), но разбиение блока на независимые сегменты
   стоит всего 0,1–0,2 % размера — это способ занять все ядра внутри одного блока.
2. Повтор замеров на машине автора, с Kanzi и в несколько потоков; файлы автора; отложенный набор.
3. Второе ядро LZ (режим fast и бинарные данные) с выбором ядра по блоку; в нём же второй уровень ссылок L2.
4. Фильтры: delta и разделение полей для записей (sao, x-ray, mr), переходы ARM64/Alpha.
5. LZP перед BWT; определение несжимаемых блоков без запуска BWT.
6. Слой L1 (дальние повторы) и эксперимент E3.
7. Фаззинг, потоковый пул, режим max.
